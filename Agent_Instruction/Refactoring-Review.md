# 컨텐츠 완료 후 리팩토링 검토

컨텐츠 하나를 끝낸 뒤, 작업한 세션과 다른 도구·세션이 그 변경을 검토할 때 쓰는 체크리스트다.
작업 규칙의 원본은 [AGENTS.md](../AGENTS.md)와 기능별 계약 문서다. 이 문서는 규칙을 다시 정의하지 않고 위반 여부를 확인할 항목만 둔다.

## 검토 방식

- **검토만 한다.** 발견 사항을 보고하고 파일은 수정하지 않는다. 수정은 사용자 승인 후 별도로 한다.
- **범위는 해당 컨텐츠의 변경분과 그 호출부·소비처다.** 관련 없는 기존 코드로 넓히지 않는다.
  변경분은 사용자가 지정한 커밋·파일 범위를 따르고, 지정이 없으면 범위를 먼저 묻는다.
- 해당 영역의 계약 문서를 [색인](README.md)에서 찾아 읽고 코드와 대조한다.
- **확인한 것만 올린다.** 실제 발생 경로(호출 순서·입력·상태)를 코드에서 확인한 문제만 보고한다.
  경로를 확인하지 못한 우려는 "미확인"으로 구분해 적고, 문제가 없으면 없다고 보고한다.
- **취향 차이는 제안하지 않는다.** 동작과 비용이 같은 이름·배치·스타일 변경, 사용처 없는 추상화 추가는 제외한다.
- 직접 실행하지 않은 컴파일·테스트·Play Mode 결과를 확인했다고 적지 않는다.

## 검토 항목

### 1. 과한 구현

- 표준 컬렉션·기존 API로 충분한데 자료구조·캐시·풀·상태 머신을 직접 만들었는가.
- 사용처가 하나뿐인 인터페이스·제네릭·설정값·확장 지점이 있는가.
- 요청에 없는 기능·옵션이 추가됐는가.

### 2. 중복 구현

- 이미 있는 공용 유틸·공용 UI 컴포넌트·이벤트 경로를 쓰지 않고 새로 만들었는가.
- 같은 로직이 이번 변경 안에서 두 곳 이상 복사됐는가.

### 3. 크래시 위험

- null·파괴된 Unity 객체·빈 컬렉션·범위 밖 인덱스·테이블 조회 실패에 대한 접근이 있는가.
- 순회 중 컬렉션 수정, 0 나눗셈, 잘못된 캐스팅, 초기화 전 접근이 있는가.
- ECS·Native 컨테이너의 해제 후 사용, 메인 스레드 밖 Unity API 호출이 있는가.

### 4. 실패 경로

- 서버 실패·타임아웃·재연결·빈 데이터일 때 화면과 상태가 어떻게 되는가.
- 빈 catch, 조용한 fallback, 기본값 대입으로 오류를 숨기지 않았는가.
- 요청 중복 전송·응답 순서 뒤바뀜에 대한 처리가 필요한데 빠졌는가.

### 5. 수명과 해제

- 이벤트 구독과 해제, 비동기 시작과 취소, 자산 로드와 해제의 짝이 맞고 소유자가 분명한가.
- 재입장·재연결·씬 전환 뒤 늦게 도착한 콜백이 이전 상태를 적용하지 않는가.
- static 필드·싱글턴이 파괴된 객체나 이전 세션 데이터를 계속 붙잡는가.

### 6. 메모리·GC·핫패스 비용

- Update·스크롤·자주 불리는 콜백 안에 할당, LINQ, 클로저, 박싱, 문자열 결합이 있는가.
- 반복 호출되는 GetComponent·Find·테이블 전체 순회가 있는가.
- 값이 바뀌지 않았는데 텍스트·레이아웃을 매번 다시 설정해 UI 리빌드를 유발하는가.
- 텍스처·머티리얼·메시를 런타임에 만들고 파괴하지 않는가.

### 7. 범용성 낮은 상수·문자열

- 코드에 박힌 Id·수치·경로·주소·색·크기 중 테이블·설정·직렬화 필드가 소유해야 할 것이 있는가.
- 사용자 표시 문구가 문자열 테이블을 거치지 않거나, 존재하지 않는 키·fallback 문구를 쓰는가.
- 같은 리터럴이 여러 곳에 흩어져 있는가.

### 8. 테이블 소유 규칙의 코드 중복

- 테이블·외부 설정이 소유하는 분류·단위·표시·조건을 코드의 목록·분기·switch로 다시 관리하는가.
- 데이터 행을 추가했을 때 소비 코드 수정 없이 적용되는가.

### 9. 신뢰 경계

- 서버가 판정해야 할 결과를 클라이언트가 확정하는가.
- 서버 변경을 대신하는 임시 우회·가짜 응답이 있는가.
- 생성 산출물(생성 코드·테이블 바이너리·프로토콜 등)을 손으로 고쳤는가.

### 10. 잔재

- 쓰이지 않는 필드·메서드·using·프리팹 참조, 주석 처리된 코드가 남았는가.
- 임시 디버그 로그, 중간 시도의 흔적, 실제 동작과 다른 주석이 남았는가.
- 임시 구현이라면 임시임과 교체 조건이 드러나 있는가.

### 11. 범위 밖 변경

- 공용 프리팹·머티리얼·폰트·공유 자산·주소·라벨을 바꿔 다른 화면이나 캐릭터까지 영향이 가는가.
- 요청과 무관한 파일이 수정됐는가. 단순 표기 통일 목적의 기존 계약 변경이 있는가.

- [동시 수정 체크리스트](Change-Checklist.md)에 해당하는 변경이라면 함께 확인할 지점을 빠뜨리지 않았는가. 실제 테스트가 잡는 범위와 수동 확인 영역을 구분했는가.
- 새로 확인한 누락 지점은 근거와 함께 체크리스트 추가 후보로 보고한다. 리뷰만 요청받은 경우 문서를 직접 수정하지 않는다.

### 12. 검증 주장과 문서

- 작업 보고의 "검증함"이 실제 실행인지 코드 검토인지 구분되는가. 미검증 항목이 남아 있는가.
- 바뀐 구조·소유권·계약이 해당 기능 문서에 반영됐는가. 문서와 코드가 다른 곳이 있는가.
- 명명·로그·이벤트 사용이 AGENTS.md의 작성 기준과 맞는가.

## 보고 형식

심각도 순으로 적고, 항목마다 아래를 포함한다.

- 심각도: **상**(크래시·데이터 손상·서버 권위 위반) / **중**(누수·성능·실패 경로 누락) / **하**(유지보수·잔재)
- 위치: 파일 경로와 줄
- 근거: 문제가 발생하는 조건과 경로
- 수정 방향: 한두 줄. 대안이 여럿이면 추천 하나를 먼저 적는다.

마지막에 검토한 범위, 문제없다고 확인한 항목 번호, 확인하지 못한 항목과 이유를 적는다.
