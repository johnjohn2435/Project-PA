# Block Gravity 화면 배치와 순수 게임 규칙

2026-11-04 사용자가 다음 작업 목록의 2번 화면 설계와 3번 게임 규칙 구현을 승인했다. UIManager가 개발 중이므로 새 게임 전용 어셈블리와 독립 테스트를 추가한다.

## 반영 상태

- 구현: 화면 배치 계산, 보드·조각·배치 검사, 네 방향 중력, 동시 줄 제거, 연쇄 반복 처리 구조와 점수, 트레이·게임 오버·보상 중복 방지.
- 검증: Unity 6000.3.16f1의 분리된 최소 검증 프로젝트에서 Edit Mode 53/53 통과. C# 컴파일 오류·경고 0. 검사한 파일과 배포한 파일의 SHA-256 일치를 확인한다.
- 동일 NUnit 테스트의 별도 .NET 실행도 53/53 통과. 서로 다른 106개 테스트를 의미하지 않는다.
- 검증 범위: 새 어셈블리만 검증했다. 전체 기존 프로젝트의 통합 컴파일·Play Mode·Android 빌드·실제 터치는 미실행이다.
- 씬/프리팹/매니저/리소스 목록은 변경하지 않았다. Unity MCP는 제공되지 않았으며, 이번 범위에는 플레이 화면 생성이 포함되지 않는다.

## 화면과 좌표 기준

- Android 세로 화면, UI 기준 1080×1920을 유지한다.
- 카메라: 직교, 회전 0, z=-10. 보드 중심이 월드 (0,0), 한 칸 1 유닛, 보드 범위 [-4,4]×[-4,4].
- 화면/Safe Area 좌표는 좌하단 원점의 실제 픽셀 좌표다. UI Canvas 좌표와 직접 혼용하지 않는다.
- PlayfieldLayout.Calculate(screenWidth, screenHeight, safeRect)가 HUD·보드·트레이의 픽셀 사각형과 카메라 위치·OrthographicSize를 반환한다.
- s=min(SafeWidth/1080, SafeHeight/1920). 좌우 여백 60s, HUD 높이 260s, 트레이 높이 360s, 사이 간격 64s.
- 보드 크기는 min(SafeWidth-120s, SafeHeight-260s-360s-128s-120s)이며 정사각형을 유지한다. 전체 묶음을 Safe Area 중앙에 둔다.
- 기준 화면의 좌하단 픽셀 사각형: HUD (60,1554,960,260), 보드 (60,530,960,960), 트레이 (60,106,960,360).
- 기준 화면에서 한 칸 120픽셀, OrthographicSize=8, 카메라 위치=(0,-0.416667,-10).
- 비율 또는 Safe Area가 바뀌면 다시 계산한다. HUD의 실제 uGUI 배치와 카메라 적용은 다음 화면 구현 단계다.
- 트레이는 폭을 3등분하여 슬롯을 배치하고 조각 중심을 슬롯 중심에 맞춘다. 조각은 미리보기에서 한 칸 0.6유닛, 드래그 시 1유닛으로 표시한다. 손가락 위 오프셋은 기준 120픽셀×s로 시작한다.

## 스프라이트 표시 기준

- 블록 기본 규격: 셀 이미지 128×128, PPU 128, 피벗 중앙. 고해상도 이미지로 바꾸면 PPU도 비례 조정하여 1유닛을 유지한다.
- 기존 캐릭터 원화의 피벗·PPU 규칙은 별도다. 블록 규격을 캐릭터에 일괄 적용하지 않는다.
- 초기 Sorting Layer는 Default를 사용하고 Order in Layer를 배경 0, 보드 10, 배치 블록 20, 배치 프리뷰 30, 트레이 조각 40, 드래그 조각 100으로 구분한다.
- 메뉴·HUD·팝업은 uGUI, 보드·블록·트레이·프리뷰는 SpriteRenderer다. HUD는 같은 배치 계산 결과를 UI 좌표로 변환해 사용한다.
- WorldToCell은 floor(world+4)로 좌하단 원점을 변환한다. 보드 바깥 좌표는 PlacementValidator가 거부한다.

## 조각 좌표와 생성

DefaultPieceSet.Create()에 고정 방향 10종을 좌표 데이터로 정의했다. 좌표는 각 조각 바운딩 박스의 좌하단을 기준으로 한다. 배치 중 회전하지 않는다.

| ID | 좌표 |
| --- | --- |
| single | (0,0) |
| line2_h | (0,0) (1,0) |
| line2_v | (0,0) (0,1) |
| line3_h | (0,0) (1,0) (2,0) |
| line3_v | (0,0) (0,1) (0,2) |
| square4 | (0,0) (1,0) (0,1) (1,1) |
| l3 | (0,0) (1,0) (0,1) |
| l4 | (0,0) (1,0) (0,1) (0,2) |
| corner3 | (0,0) (1,0) (1,1) |
| t4 | (0,0) (1,0) (2,0) (1,1) |

구현 선택: 기존의 불가능한 “3칸 T”를 4칸 T로 보정하고, L3과 코너3은 다른 방향으로 구분했다. 기본 가중치는 모두 1이며 튜닝 전 중립값이다. PieceBag은 지정 seed와 가중치를 사용하여 매번 독립 추첨한다. 이름의 Bag은 비복원 셔플을 의미하지 않는다. PieceDefinition은 좌표와 가중치를 주입하는 직렬화 가능한 순수 C# 데이터이며 Unity 에셋/JSON 로딩 어댑터는 후속 화면 연결 단계다.

## 규칙과 결과 전달

- BoardState: 0은 빈칸, 양의 정수는 블록 ID. 복사와 조회 경계 검사.
- PlacementValidator: 경계·겹침·실제 조각 좌표 검사, 트레이 전체 배치 가능성 검사.
- GravityResolver: 셀을 독립적으로 압축하며 블록 ID와 이동 전후 좌표를 반환. 방향은 Down → Left → Up → Right.
- LineDetector/LineClearResolver: 가로·세로 완성 줄을 동시에 탐색하고 교차 셀은 한 번만 제거.
- ScoreCalculator: 셀당 10, 줄 1/2/3/4개=100/300/600/1000, 5줄부터 줄당 400 추가. 삭제 점수에 연쇄 단계 배수. 코인은 min(100,score/250).
- BlockGravitySession: 배치 → 현재 중력 정렬·삭제 반복 → 5회마다 방향 변경·재정렬·삭제 반복 → 트레이 소진 시 3개 리필 → 전체 배치 불가 검사.
- 같은 턴의 중력 변경 후 삭제도 연쇄 단계를 이어 사용한다. 점수는 long으로 계산한다. 기존 저장 데이터의 int 점수로 연결할 때는 저장 경계에서 범위를 별도로 처리한다.
- TryPlace는 성공 시 TurnResult의 단계별 보드 스냅샷과 이동 정보를 반환하고 AwaitingPresentation 상태가 된다. 완료 전 추가 TryPlace는 Busy다.
- Presenter가 프레임을 모두 재생한 후 CompletePresentation을 호출하면 WaitingForInput 또는 GameOver가 된다. 입력/일시정지 차단은 UI·Presenter의 책임이다.
- TryClaimReward는 GameOver 이후 한 번만 성공한다. 실제 저장/보상 지급 연동은 후속 단계다. 저장 실패 복구까지 보장하는 영속 트랜잭션은 아니다.
- 재시작은 새로운 세션을 생성한다. 캐릭터·설정·최고 점수 등의 앱 데이터는 별도 매니저가 유지한다.
- Board·Tray·TurnFrame을 외부에서 바꿔도 세션 원본은 오염되지 않는다. 잘못된 배치는 턴 수·점수·트레이·랜덤 추첨을 변경하지 않는다.

## 연쇄에 관한 규칙 제약

빈 장애물 없는 직사각형 보드에서 모든 셀을 한 방향으로 압축한 뒤 완성 가로·세로줄을 전부 동시에 제거하면, 동일 방향의 추가 연쇄는 발생하지 않는다. 정렬된 각 열의 높이에서 공통으로 꽉 찬 행이 한 번에 제거되고 꽉 찬 열도 제거되므로, 추가 정렬 후 새 완성 줄이 남지 않는다. 안정 상태에는 빈 가장자리 행과 열이 생겨 바로 다음 방향으로 압축해도 새 완성 줄은 생기지 않는다.

따라서 현재 명세를 따른 일반 세션에서는 한 턴에 여러 단계 연쇄나 중력 변경만으로 추가 삭제가 자연스럽게 발생하지 않는다. 반복 처리와 배수 계산은 구현했지만 다단 연쇄가 실제 게임에서 발생한다고 보고하지 않는다. 비정렬 보드에서 삭제→중력을 수행하면 새 줄이 생기는 하위 연산 테스트와 연쇄 배수 테스트는 별도로 통과했다. 다단 연쇄를 핵심 재미로 유지하려면 삭제 시점·고정 블록 등 게임 규칙 조정이 필요하다.
