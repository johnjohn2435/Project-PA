PROJECT PA · 2026년 11월 4일

기본 명세와 추가 결정 항목

여러 미니게임을 담은 Unity 2D 게임을 만든다. 메뉴와 HUD는 uGUI로, 플레이 공간은 SpriteRenderer로 구성하며 이미지 리소스는 ComfyUI로 제작한다.

기존 명세 유지렌더링 역할 확정후속 게임 규칙 구현 반영

uGUI

메인 메뉴 · 게임 선택 · 점수와 타이머 · 일시정지 · 결과 화면

SpriteRenderer

플레이 배경 · 캐릭터 · 보드 · 블록 · 조각 트레이 · 배치 프리뷰

하단 조각 트레이도 실제 플레이 공간에 속한다. 같은 이미지 에셋을 UI와 플레이에서 재사용할 수 있지만, 각각의 표시 컴포넌트는 용도에 맞게 구분한다.

확정된 기본 방향

항목기준
게임 구성여러 미니게임을 하나의 허브에서 선택하는 Unity 2D 게임. 첫 완성 대상은 Block Gravity.
UIuGUI와 TextMeshPro로 메뉴, 게임 선택, 점수·타이머 등 HUD, 일시정지·결과 화면을 구성한다.
플레이 표현배경, 캐릭터, 보드, 블록, 조각 트레이와 배치 프리뷰 등 플레이 공간의 시각 요소는 SpriteRenderer를 사용한다.
이미지 제작ComfyUI를 사용한다. 캐릭터 디자인과 세부 아트 규격은 관련 아트 결정 기록을 따른다.
플랫폼과 화면Android 세로 화면, UI 기준 해상도 1080×1920, Safe Area. 렌더링 상한은 120fps이며 중급 Android의 성능 목표는 60fps다.
입력기존 명세의 모바일 단일 터치와 Editor 마우스 조작을 유지한다.
진행 흐름BootScene → SelectScene → GameScene. 로그인 없이 게스트 플레이가 가능하다.
저장과 리소스선택 캐릭터, 설정, 최고 점수와 코인은 로컬 저장. 게임 리소스는 로컬 빌드에 포함하고 부트에서 준비한다. 원격 패치는 사용하지 않는다.
후속 구현 반영 · 카메라·플레이 영역과 블록 규격, 조각 좌표는 최신 화면 배치와 게임 규칙에 정리했다. 아래 표는 초기 검토 이력이다. 캐릭터 애니메이션과 판 중간 저장은 미정이다.

초기 검토 항목

아래는 후속 구현 전의 검토 초안이다. 플랫폼, 화면 방향, 첫 미니게임과 씬 흐름은 기존 명세대로 유지한다.

항목정할 내용설계 초안 및 확인 사항
카메라와 플레이 영역화면 비율이 달라질 때 보드·조각 트레이·HUD의 배치와 여백을 어떻게 유지할지.직교 카메라를 사용하고 보드와 트레이가 HUD를 제외한 영역에 모두 들어오도록 맞추는 안.
플레이 스프라이트 규격보드 한 칸의 월드 크기, 블록 PPU, 피벗, 레이어별 표시 순서.보드 셀을 기준으로 규격을 정한다. 기존 캐릭터 원화 규격은 유지하며 더미 전용 PPU 256을 전체 리소스에 일괄 적용하지 않는다.
캐릭터 애니메이션정지 이미지에 이동·크기 변화를 줄지, 프레임 애니메이션이나 뼈대 애니메이션을 사용할지.첫 플레이 완성에는 단일 스프라이트와 이동·크기 연출을 사용하고 캐릭터 애니메이션 확장은 후속으로 두는 안.
진행 중인 판의 저장앱 종료 후 이어하기, 일시정지 중 중단, 중도 포기 시 보상 여부.MVP는 판 중간 저장 없이 결과와 설정만 저장하고, 강제 종료한 판은 새로 시작하는 안. 포커스 상실 시 드래그 취소·일시정지는 기존 요구사항이다.
첫 게임 조각 목록기존 4.3절의 “3칸 T”가 의미하는 셀 좌표와 “3칸 L / 3칸 코너”의 구분.상하좌우로 연결된 일반적인 T형은 최소 4칸이다. 4칸 T를 뜻하는지 확인하고 각 조각을 좌표로 확정한다. L과 코너는 중복 모양인지, 방향별 항목인지 확인한다.
먼저 보드·트레이·HUD의 화면 배치와 조각별 셀 좌표를 정하면 첫 플레이 구현의 기준이 생긴다. 최종 원화가 나오기 전에는 임시 스프라이트로 동작을 확인할 수 있다.
구현에 반영할 경계
  • 게임 규칙과 점수 계산은 순수 C# 로직을 유지하고 SpriteRenderer와 UI는 결과를 표시한다.
  • UI가 소비한 입력은 게임 오브젝트에 전달하지 않는다. 일시정지·결과 팝업이 열리면 플레이 입력을 차단한다.
  • UI 해상도 대응과 플레이 카메라 범위는 별도로 관리한다.
  • 표시 문구는 기존 문자열 테이블로 관리한다. 이미지 안에 문구를 고정하지 않는다.

120fps와 프레임 끊김 점검

부트·선택·게임 씬에 적용되는 공통 상한을 60fps에서 120fps로 올렸다. Android에서 실제 표시 속도는 화면 주사율과 기기 성능에 따라 달라진다. Android 프레임 페이싱과 점진적 가비지 컬렉션은 이미 켜져 있다.

  • 흔들리는 바닥의 점수와 생존 시간. 시간은 0.1초 단위로 보이지만 HUD는 매 프레임 문자열을 만든다. 에디터에서 같은 플레이 상태로 HUD를 120번 갱신하자 GC.Alloc 1,320회가 기록됐다. 점수나 표시할 시간이 바뀔 때만 문구를 다시 만들고, 언어·게임 상태가 바뀌면 즉시 갱신하는 것이 첫 개선 후보다.
  • 원판의 테두리. 준비·종료 화면에서도 매 프레임 원판 테두리 64개를 다시 배치하고 메시 경계를 계산한다. 원 둘레 좌표를 미리 계산하고 기울기나 크기가 바뀔 때만 테두리와 메시를 갱신하는 방법을 검토할 수 있다.
  • 실기기에서 비교할 값. 120Hz Android에서 적이 몰리는 동일한 구간을 반복해 CPU·GPU 시간과 가장 느린 1%의 프레임을 비교한다. 120fps의 프레임당 예산은 약 8.33ms이고, 60fps는 약 16.67ms다.

검증용 Unity 에디터의 Play Mode에서 공통 런타임 설정을 확인했다. Android 실기기에서의 지속 FPS와 발열은 추후 측정 항목이다. Unity의 플랫폼별 프레임 설정 · Android 프레임 페이싱

기존 문서와 연결

전체 MVP 명세의 6.4·6.5절에 이번 내용을 추가했다. 변경 이력은 프로젝트 결정 기록, 이미지 규격은 ComfyUI 원화 제작 안내를 함께 본다. 이번 요약과 충돌하는 과거 내용에는 최신 결정 기록을 우선한다.
